# Service Generation Use Cases for Load Testing

## Purpose
This document defines use cases for generating test services that will be deployed and subjected to various load testing scenarios. These use cases cover a comprehensive range of HTTP interaction patterns, payload sizes, and testing objectives to thoroughly evaluate system performance, stability, and scalability.

## Use Case Categories

### 1. Minimal Overhead Operations
### 2. Standard Business Operations
### 3. Data Transfer Operations
### 4. High Volume Operations
### 5. Network Saturation Operations
### 6. Long-Running Operations

---

## USE CASE 1: Health Check / Ping
**Category:** Minimal Overhead Operations
**Objective:** Establish baseline latency and maximum request throughput

### Request
- Method: GET
- Path: /health
- Headers: None required
- Body: None

### Response
- Status Code: 200 OK
- Headers: Content-Type: text/plain
- Body: None (or single word "OK")
- Size: ~0-10 bytes

### Testing Profile
- **Stress Testing:** 10,000+ requests/second per agent
- **Soak Testing:** Sustained 5,000 requests/second for 24+ hours
- **Expected Latency:** p50 < 5ms, p99 < 20ms
- **Use Case:** Verify overhead of routing, connection handling, and basic request processing

## Best Practices for Load Testing

### Payload Size Guidelines

**Extra Small (XS): 0-1 KB**
- Health checks, simple status endpoints
- Expected throughput: 5,000-10,000 req/s per agent
- Use for: Baseline performance, routing overhead

**Small (S): 1-10 KB**  
- Standard API operations, single entities
- Expected throughput: 1,000-5,000 req/s per agent
- Use for: Typical business logic, CRUD operations

**Medium (M): 10-100 KB**
- Collection queries, bulk operations  
- Expected throughput: 200-1,000 req/s per agent
- Use for: List operations, moderate batch processing

**Large (L): 100 KB - 10 MB**
- Report generation, file uploads
- Expected throughput: 20-200 req/s per agent  
- Use for: Data-intensive operations, document handling

**Extra Large (XL): 10 MB - 100 MB**
- Large file transfers, bulk data imports/exports
- Expected throughput: 5-50 req/s per agent
- Use for: Data migration, batch imports, exports

**XXL: 100 MB+**
- Network saturation testing, extreme scenarios
- Expected throughput: 1-20 req/s per agent (scale agents)
- Use for: Infrastructure limits, bandwidth testing

### Testing Phases

**Phase 1: Baseline (15-30 minutes)**
- Single agent, low load (10% of target)
- Establish baseline latency and throughput
- Verify service functionality

**Phase 2: Ramp Up (30-60 minutes)**
- Gradually increase load from 10% to 100% of target
- Monitor for degradation points
- Identify scaling thresholds

**Phase 3: Stress Test (1-4 hours)**
- 100-150% of expected production load
- Short bursts to 200% capacity
- Identify breaking points and limits

**Phase 4: Soak Test (24-168 hours)**
- 60-80% of capacity
- Extended duration to identify leaks and degradation
- Monitor memory, connections, file descriptors

**Phase 5: Spike Test (30-60 minutes)**
- Sudden jumps from 20% to 150% load
- Hold for 5-10 minutes, return to baseline
- Test auto-scaling and recovery

**Phase 6: Network Saturation (2-8 hours)**
- Scale agents to saturate network bandwidth
- Use XL/XXL payloads
- Monitor network interface utilization >80%
- Verify no packet loss or connection drops

### Kubernetes-Specific Considerations

**Resource Allocation:**
- Services: 250m-1000m CPU, 256Mi-2Gi memory per pod
- Agents: 100m-500m CPU, 128Mi-512Mi memory per pod
- Monitor pod CPU throttling and OOM kills

**Network Bandwidth:**
- Standard Kubernetes nodes: 1-10 Gbps per node
- Pod-to-pod bandwidth: 1-5 Gbps depending on CNI
- Network saturation target: >80% sustained utilization
- Use XXL payloads with scaled agents to reach saturation

**Scaling Strategy:**
- Horizontal Pod Autoscaler (HPA): CPU >70%, Memory >80%
- Scale agents proportionally to services (maintain 1:1 or 2:1 ratio)
- For network saturation: Scale both to 20-50 pods each

**Monitoring:**
- Request latency (p50, p90, p95, p99)
- Error rate (<0.1% for success)
- CPU utilization (target: 60-80%)
- Memory usage (with growth trend)
- Network throughput (Mbps/Gbps)
- Connection pool exhaustion
- Database connection count (if applicable)

## Success Criteria

### Performance Sign-off Requirements

**Latency (per use case category):**
- Minimal: p99 < 50ms
- Standard: p99 < 200ms
- Data Transfer: p99 < 1000ms
- High Volume: p99 < 5000ms
- Network Saturation: p99 < 15000ms

**Throughput:**
- Meet or exceed target requests/second
- No degradation >10% during soak test
- Recovery to baseline within 5 minutes after spike

**Reliability:**
- Error rate <0.1% under normal load
- Error rate <1% during stress test
- Zero crashes or OOM kills during soak test

**Stability:**
- Memory growth <5% per 24 hours
- No memory leaks detected over 7-day soak
- CPU utilization stable (±10% variance)
- Connection pools remain healthy

**Scalability:**
- Linear performance improvement with horizontal scaling
- Auto-scaling triggers appropriately
- Scale-down without service disruption

**Network:**
- Achieve >80% network interface utilization
- Zero packet loss during saturation test
- Maintain latency SLAs during saturation
- Connection reuse and keepalive functioning
